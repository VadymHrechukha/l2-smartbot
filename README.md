# SmartBot for L2J Mobius — Interlude C6

SmartBot is an experimental managed fake-player system for Lineage 2, adapted from [PlayerExplains/l2-smartbot](https://github.com/PlayerExplains/l2-smartbot) for the **MobiusDevelopment/L2J_Mobius** codebase.

The project combines deterministic in-game bot behavior with optional local chat responses generated by [Ollama](https://ollama.com/). The intended target is **L2J Mobius Interlude (C6)**, not the original project's L2J Scions of Destiny (C4) / `net.sf.l2j` API.

> **Development status:** This README describes the Mobius adaptation and its intended behavior. Treat the port as experimental until the current checkout has passed a clean Mobius build and in-game tests. Features listed below should be considered implemented only where they are present and verified in your working tree.

## What this project is

SmartBot adds managed fake-player characters to an L2J server. The original project supplies the bot presets, command concepts, basic combat/support routines, Ollama-backed chat, short-term memory, and a plain-text knowledge system. This version adapts those ideas to Mobius' package layout, APIs, configuration loader, admin-command registration, server lifecycle, and player model.

Ollama is used for **optional conversational replies**. Core combat actions—movement, targeting, attacking, healing, buffs, and other game operations—should remain controlled and validated by server-side Java logic. An LLM response must never be treated as an unrestricted instruction to execute game actions.

## Target and compatibility

- **Server source:** [MobiusDevelopment/L2J_Mobius](https://github.com/MobiusDevelopment/L2J_Mobius)
- **Chronicle target:** Interlude C6 branch / datapack
- **Operating system for this setup:** Windows 11
- **Optional local LLM runtime:** Ollama
- **Database:** use the database engine and schema setup already supported by your selected Mobius branch
- **Language/runtime:** use the JDK version required by the exact Mobius checkout; do not assume the JDK version from another branch is compatible

The original SmartBot source uses legacy classes such as `net.sf.l2j.gameserver.model.actor.instance.L2PcInstance`. Mobius uses a different API and package structure. This version is therefore a **source port**, not a drop-in plugin: compile against the actual Mobius checkout and verify method signatures before making further changes.

## Features and planned behavior

The original SmartBot project describes the following features. Their availability in the Mobius port depends on the state of the current code and should be verified during testing.

### Bot presets

| Preset | Intended role | Behavior |
|---|---|---|
| `ARCHER` | Ranged fighter | Bow combat, soulshots, occasional stun skill |
| `MAGE` | Mage | Uses available offensive magic |
| `HEALER` | Healer | Heals and supports party members; resurrection where supported |
| `BUFFER` | Support | Applies appropriate buffs to eligible party members |
| `DAGGER` | Melee fighter | Dagger combat and available blow skills |
| `TANK` | Tank | Sword-and-shield combat and available aggro skills |

These presets originate in a C4-oriented project. **Class IDs, skill IDs, item IDs, skill availability, and skill names must be checked against the Interlude datapack.** Do not assume that a skill ID or preset from C4 is correct for Interlude.

### Bot management

The intended management flow includes:

- Creating named bots using a GM/admin command.
- Keeping bot records in a database so managed bots can be restored after a restart.
- Following or unfollowing a player.
- Despawning a bot without necessarily deleting its stored record.
- Deleting a bot and its stored record.
- Stopping a bot or setting it to idle.

### Party and gameplay support

The original behavior includes follow, assist, attack, and stop modes; party-invite support; healing and buffing support; and preset-specific combat routines. The Mobius port must use Mobius' own player, party, world, skill, inventory, movement, and AI APIs.

Bots should only act through validated server-side code. LLM-generated text should not directly determine targets, skill IDs, coordinates, item use, or other privileged game actions.

### Ollama chat

- Optional local chat responses using an Ollama model.
- Per-bot short-term conversation history.
- A small file-based knowledge collection for Lineage 2 facts.
- A fallback path for basic behavior when Ollama is unavailable, where supported by the current implementation.

Ollama chat is separate from autonomous gameplay logic. This project should not be described as an LLM-controlled combat AI unless that functionality is separately implemented and tested.

## Architecture in the Mobius port

The port should follow Mobius conventions rather than recreating the original `net.sf.l2j` package tree.

The migration work has used or identified the following Mobius API counterparts. **Confirm each symbol in the exact branch before relying on it**, because package names and signatures can change between Mobius branches.

| Original L2J API | Mobius-side counterpart identified for this port |
|---|---|
| `L2PcInstance` | `org.l2jmobius.gameserver.entity.actor.Player` |
| `L2World` | `org.l2jmobius.gameserver.entity.World` |
| `L2Party` | `org.l2jmobius.gameserver.entity.groups.Party` |
| `SkillTable` / `L2Skill` | `org.l2jmobius.gameserver.data.xml.SkillData` / `org.l2jmobius.gameserver.mechanics.skill.Skill` |
| `CharTemplateTable` / `L2PcTemplate` | `org.l2jmobius.gameserver.data.xml.PlayerTemplateData` |
| `L2DatabaseFactory` | `org.l2jmobius.commons.database.DatabaseFactory` |
| `ThreadPoolManager` | `org.l2jmobius.commons.threads.ThreadPool` |
| `Rnd` | `org.l2jmobius.commons.util.Rnd` |
| `L2MonsterInstance` | `org.l2jmobius.gameserver.entity.actor.instance.Monster` |
| `L2Object` | `org.l2jmobius.gameserver.entity.WorldObject` |
| `IItemHandler` / `ItemHandler` | `org.l2jmobius.gameserver.handler.ItemHandler` |
| `L2GameClient` | `org.l2jmobius.gameserver.network.GameClient` |
| `Config.BOT_*` settings | Custom `SmartBotConfig`, loaded through Mobius `ConfigLoader` |
| Legacy admin command handler | Mobius `IAdminCommandHandler` / `AdminCommandHandler` API |

This table is a migration aid, not a substitute for source inspection. For example, player creation, item instances, skill activation, AI intentions, chat packets, party-request packets, and persistence methods can have important signature or lifecycle differences.

## Requirements

1. A checked-out, working copy of the intended **L2J Mobius Interlude** source and datapack.
2. The JDK version required by that checkout.
3. The database server and schema setup required by the selected Mobius branch.
4. A clean baseline build of Mobius before adding SmartBot.
5. Ollama only if local AI chat is desired.
6. A local Ollama model compatible with your available RAM/VRAM.

For this Windows 11 setup, keep the Mobius source, SmartBot source/reference, test server, and Ollama model data in separate directories where practical. Do not patch the original upstream repository directly; use a separate working copy or feature branch.

## Ollama setup (optional)

1. Install Ollama from [ollama.com/download](https://ollama.com/download).
2. Open a terminal and pull/start a model. For example:

   ```powershell
   ollama run gemma3
   ```

   Use the exact model name configured in `SmartBotConfig`. The command above is only an example; it does not mean that `gemma3` is the only supported model.
3. Verify that Ollama is reachable locally. The original SmartBot implementation uses the generate API endpoint:

   ```text
   http://127.0.0.1:11434/api/generate
   ```

4. Configure the Mobius SmartBot settings to use the same endpoint and installed model.
5. Test chat responses independently from bot movement and combat.

If Ollama is stopped or the model cannot be loaded, the game server should continue to run. The exact fallback behavior depends on the current port implementation. LLM requests should run asynchronously, with timeouts and bounded response sizes, rather than blocking a game packet-processing thread.

## Installation and integration

The exact installation steps depend on the current source tree. Use the steps below as a checklist and verify every item against your working checkout.

### 1. Start from a clean Mobius working copy

- Build and run the unmodified Mobius source first.
- Create a separate branch or working copy for SmartBot.
- Keep the original `PlayerExplains/l2-smartbot` repository as a reference; do not copy its legacy package tree into Mobius unchanged.
- Review the migration diff before applying changes. Do not blindly apply machine-specific IDE files or paths.

### 2. Add the SmartBot Java code

Keep SmartBot classes under the Mobius package hierarchy used by the port. The migration has used the following conceptual components:

- `SmartBotManager` — manages bot records and active bots.
- `SmartBotController` — coordinates bot behavior.
- `BotLlmService` — handles optional Ollama chat.
- `SmartBotDao` — reads/writes persistent bot data.
- `BotMemory` — stores short-term conversation history.
- `SmartBotData` — persisted bot state.
- `SmartBotKnowledge` — loads and selects text knowledge facts.
- `SmartBotPreset` and `SmartBotRole` — define presets and roles.
- `AdminSmartbot` — admin commands.

Names and locations should match the actual working tree. Avoid duplicating classes if the port already contains them.

### 3. Register configuration

The port uses a dedicated custom configuration class, `org.l2jmobius.gameserver.config.custom.SmartBotConfig`, intended to be loaded through Mobius' `ConfigLoader`.

Check that:

- The configuration class is actually registered/loaded during startup.
- Defaults and property names agree with the code.
- Invalid values are handled safely.
- Ollama URL/model and reply limits are configurable.
- Bot ranges, healing thresholds, follow distance, memory limits, and knowledge limits are configurable where implemented.

Do not add legacy `BOT_*` fields to a monolithic `Config.java` just because the original README does so. Follow the configuration pattern used by the target Mobius branch.

### 4. Register admin commands

Use Mobius' admin command API and command registration mechanism. The migration notes identify `AdminCommandHandler.getInstance().registerHandler(...)` and the Mobius `IAdminCommandHandler` methods as the relevant pattern, but confirm their exact signatures in the target branch.

Also verify that the command aliases are permitted by the server's admin command configuration, including `dist/game/config/AdminCommands.xml` if that file exists in the selected checkout.

A command class compiling is not sufficient: test each command in-game with an authorized GM account.

### 5. Create the SmartBot database table

The original project stores managed bots in a `smart_bots` table. The Mobius port must use the database conventions and connection APIs of the selected branch.

Before applying SQL:

- Inspect the current SmartBot DAO and SQL files.
- Check whether the table already exists.
- Verify column names, SQL types, primary key, and defaults against the DAO.
- Back up the test database.
- Apply schema changes to the development database first.

The original README's table definition is a reference only; do not assume it is automatically correct for the Mobius port.

### 6. Integrate startup and shutdown

Verify the server lifecycle integration in the current source:

- Load SmartBot configuration before it is used.
- Load knowledge files during startup.
- Restore managed bot records at the appropriate stage of world/server initialization.
- Save or update bot state during normal operation where required.
- Persist relevant state and shut down SmartBot services safely during server shutdown.

Do not register duplicate hooks. The migration notes mention hooks in `GameServer.java` and `Shutdown.java`; inspect the current code to confirm that these are present, correctly ordered, and called only once.

### 7. Integrate chat and party handling

The original project hooks into local chat and party invites. The Mobius port must use the actual Mobius packet classes and semantics.

Verify that:

- Nearby chat can be processed without blocking the packet thread on an Ollama HTTP request.
- Bot messages do not create a recursive chat/LLM loop.
- Party requests involving managed bots are handled before normal player-client assumptions are made.
- Managed bots without a normal `GameClient` are not passed into code that requires one.
- Exceptions and timeouts do not disrupt normal player chat or party handling.

The migration notes identify `Say2.java` and `RequestJoinParty.java` as integration points in the target source, but inspect the exact branch before editing.

### 8. Install the knowledge files

Place the plain-text knowledge files in the location expected by the current implementation. The planned location is:

```text
<server-root>/config/smartbot/knowledge/
```

The original format is one fact per line, optionally preceded by tags:

```text
[level, farm, interlude] Example Lineage 2 knowledge fact.
[buff, fighter] Example fighter-buff knowledge fact.
[buff, mage] Example mage-buff knowledge fact.
```

Only use facts that are appropriate for Interlude. Remove or rewrite C4-specific claims, skills, zones, level ranges, and mechanics that are not correct for the target datapack.

Check the log at startup to confirm the directory was found and facts were loaded. If the directory is missing, the server should fail gracefully rather than crashing.

## Admin commands

The original SmartBot project documents these command concepts. Exact command names and availability must be confirmed in the Mobius port and configured admin-command list.

| Command concept | Purpose |
|---|---|
| `//bot_create <name> <preset>` | Create a managed bot |
| `//bot_follow` | Make the targeted bot follow the GM/player |
| `//bot_unfollow` | Clear its follow target |
| `//bot_despawn` | Remove it from the world while retaining its record, if implemented |
| `//bot_delete` | Remove the bot and its stored record, if implemented |

Example preset names from the original project:

```text
ARCHER
MAGE
HEALER
BUFFER
DAGGER
TANK
```

Example command, if enabled in your build:

```text
//bot_create Mark ARCHER
```

These examples document the intended interface; they are not proof that a command is registered or working in every build.

## Player chat commands

The original project describes local-chat commands such as:

| Command | Intended behavior |
|---|---|
| `follow` / `<bot name> follow` | Follow the player |
| `follow all` / `all follow` | Tell nearby managed bots to follow |
| `assist` | Assist the player's target or provide role-appropriate support |
| `assist all` / `all assist` | Tell nearby managed bots to assist |
| `attack` | Attack a nearby monster, if allowed by the current behavior |
| `attack all` / `all attack` | Tell nearby managed bots to attack |
| `stop`, `wait`, `hold` | Stop or idle |
| `buff` / `buffs` | Request support buffs |
| `party` / `invite` | Start or handle a party-invite flow |

Only commands actually wired into the Mobius port should be advertised as supported. Test command parsing for names with spaces, case differences, ambiguous bot names, and ordinary player chat that happens to contain a command word.

## Behavior and balancing notes

The original C4 implementation uses fixed candidate skill and item IDs. For Interlude, validate all of the following against the active datapack:

- Player class IDs and templates.
- Weapon/armor and shot item IDs.
- Attack, stun, dagger, aggro, healing, resurrection, and buff skill IDs.
- Skill levels, magic/physical skill type, reuse times, and target restrictions.
- Buff availability and class restrictions.
- Inventory weight and item-stack behavior.
- Party rules, range checks, movement, and AI intention APIs.

Prefer resolving skills and items through Mobius data APIs and validating them at runtime rather than assuming a hard-coded C4 ID is valid. Do not let bots cast unavailable skills or bypass normal game rules.

## Testing checklist

Run these tests on a local development server before considering the port ready.

### Build and startup

- [ ] Unmodified Mobius baseline builds successfully.
- [ ] SmartBot changes build with the JDK required by this branch.
- [ ] Configuration loads with defaults and with a custom Ollama model.
- [ ] The server starts with Ollama running and with Ollama stopped.
- [ ] Knowledge files load; a missing knowledge directory is handled safely.
- [ ] The database table matches the DAO schema.
- [ ] Startup restores valid bot records without duplicating bots.
- [ ] Shutdown saves required state and exits cleanly.

### Admin and persistence

- [ ] Each admin command is registered and permission-controlled.
- [ ] A bot can be created with each supported preset.
- [ ] Duplicate names and invalid presets are rejected safely.
- [ ] Despawn and delete have distinct, expected effects.
- [ ] Bots restore after a server restart without duplicate records.

### In-game behavior

- [ ] Follow, unfollow, assist, attack, and stop work.
- [ ] Party invitations work in both relevant directions.
- [ ] Healer and buffer behavior respects party, range, and target rules.
- [ ] Each combat preset uses only valid Interlude skills and equipment.
- [ ] Bots do not become stuck due to overload, movement, or invalid targets.
- [ ] Normal player chat and party handling continue to work.

### Ollama and robustness

- [ ] Chat replies work with the configured model.
- [ ] A slow or unavailable Ollama endpoint does not freeze packet processing.
- [ ] Request timeouts and response length limits are enforced.
- [ ] Invalid or unexpected model output is treated as text, not an executable action.
- [ ] Bot chat does not trigger recursive replies.
- [ ] Errors are logged without flooding the server log.

## Troubleshooting

### The port does not compile

1. Confirm the checkout is the intended Mobius Interlude branch.
2. Build unmodified Mobius first.
3. Check the first compiler error rather than fixing only downstream errors.
4. Verify the actual package and method signatures in the source.
5. Avoid global package-name replacements; similarly named APIs can have different semantics.
6. Rebuild after each small, logically related change.

### A bot does not move or gets stuck

- Check whether it is overloaded.
- Check that it has valid equipment and inventory contents.
- Inspect the target and movement/AI intention calls for the current Mobius API.
- Check server logs for invalid targets, movement failures, or exceptions.
- Verify that the bot is not trying to use a skill or item unavailable in Interlude.

### Ollama replies do not work

1. Start Ollama and confirm the model is installed.
2. Confirm the URL is reachable at `http://127.0.0.1:11434/api/generate`.
3. Check the model name in `SmartBotConfig`.
4. Inspect server logs for connection failures, timeouts, malformed responses, or JSON parsing errors.
5. Test a normal chat response separately from combat behavior.

### The bot does not restore after restart

- Check the `smart_bots` table and DAO queries.
- Confirm startup restore runs after the required world/player services are initialized.
- Check whether bot records are marked active.
- Verify the stored class/template ID and spawn coordinates are valid for the current datapack.

## Known limitations

- The upstream project was designed for a C4-oriented L2J core; this port targets Mobius Interlude and requires branch-specific validation.
- The file-based knowledge system is simple retrieval, not embeddings or a vector database.
- The original chat integration uses direct HTTP calls to Ollama.
- The original combat logic is primarily rule-based and uses fixed skill candidates; it is not automatically transformed into LLM-driven combat by adding Ollama.
- C4 skill, item, class, and zone assumptions may not be valid in Interlude.
- Mobius APIs and lifecycle behavior can differ between branches.
- Features should be considered experimental until the test checklist has passed.
